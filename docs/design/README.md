# Design diagrams

PlantUML sources for the crate's structure. Rendered output is not committed —
regenerate with the command below.

| File | What it shows |
|---|---|
| `01-component.puml` | the two crates, and why there are two |
| `02-pipeline.puml` | the three stages and what each is allowed to know |
| `03-pipeline-status.puml` | what is actually wired today, and where the gap is |
| `04-class-core.puml` | `Extraction` / `Extracted` / `Reason` and the trait contract |
| `05-class-resolution.puml` | the `Raw` → `Parsed` typestate |
| `06-class-meta.puml` | the `syn::Meta` translation layer |
| `07-class-extractors.puml` | the concrete extractors and how they nest |

## Rendering

The PlantUML server in a container, then POST each file:

```sh
docker run -d --rm -p 8080:8080 --name plantuml plantuml/plantuml-server:jetty
```

Once it is up:

```sh
cd docs/design
for f in *.puml; do
  curl -s --data-binary @"$f" -X POST \
    -H 'Content-Type: text/plain' \
    "http://localhost:8080/svg" -o "${f%.puml}.svg"
done
docker stop plantuml
```

Or without a container, if `plantuml` is installed locally:

```sh
plantuml -tsvg docs/design/*.puml
```

## Reading order

`01` and `02` first — they carry the two decisions everything else follows from:
the proc-macro export constraint, and the rule that **extraction carries,
processing understands**. `03` is the honest status. The class diagrams are
reference.

## Note on the annotations

Notes in these diagrams quote the `#id` annotations in the source. Where a
diagram and the code disagree, **the code is right and the diagram is stale** —
these are generated by hand and nothing keeps them in sync.
